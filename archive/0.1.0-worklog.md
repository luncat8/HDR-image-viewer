# 0.1.0 worklog

## Steps

1. Read `draft.txt`, found an empty project with only an `index.html` holding a bare canvas.
2. Split the work along the seam that already existed in the request: *collect files*,
   *show one image*, *wire input to output*. `js/files.js`, `js/viewer.js`, `js/app.js`.
3. `js/files.js` — pickers, drop walk, extension filter, natural path order.
4. `js/viewer.js` — canvas, contain fit, one live object URL, token-guarded loads.
5. `js/app.js` + `index.html` + `css/app.css` — key map, HUD, drop highlight, empty state.
6. Node harnesses under `experiments/`; no browser is installed in this environment, so each
   module is driven against stubs instead of a real DOM.

## Bugs found by the harnesses

- **Paths crossed during a directory walk.** The async `readEntries` callback closed over the
  loop's `var top`, which the next iteration had already reassigned, so files landed under the
  wrong parent directory. Fixed by moving the per-entry work into its own function so each
  callback owns its path as a parameter.
- **`p2` sorted after `p10`.** The digit comparison shortcut compared digit-run *lengths*,
  which is the common but wrong reading of natural order. Now leading zeros are skipped and
  the runs compare by value, so `p2 < p10 < p250`.
- **Space was swallowed with a single image.** `preventDefault` ran before the list-length
  check. Reordered, so keys only claim the key when there is somewhere to move.
- **The HUD reversed paths.** `direction: rtl` on a path keeps the tail visible, but it also
  lays the segments out right-to-left and renders `photos/img.png` as `img.png/photos`.
  Replaced with a basename in the label and the full path in the tooltip.

## Reported after the first pass

### 1. Dropping reported "no images found"

`webkitGetAsEntry()` was being called from the `drop` handler. Chrome invalidates the
`DataTransferItem` list once the drop has fired, so every call returned `null`, the code
fell through to `dataTransfer.files` — which is empty for a dropped *folder* — and reported
nothing found. Plain file drops happened to work, which is why it looked intermittent.

Fixed by capturing entries on `dragenter`, while the drag is still live, and passing them
into `Files.fromDataTransfer` at drop. `Files.captureEntries` is a separate exported function
for exactly this. `dragleave` clears the capture so a stale drag cannot feed the next one, and
`fromDataTransfer` still captures live when no entries were passed, so a drop that never
entered the window still works.

The regression test builds a real mock: a live transfer whose `webkitGetAsEntry` returns a
directory, then a *spent* transfer at drop time that returns `null` and has no files. With the
capture removed the test fails; with it, the folder walks.

### 2. The canvas destroyed HDR content

The stage was a 2D canvas. A 2D canvas is 8 bits per channel, so an HDR frame drawn into it
is clamped to SDR — the image looked washed out and flat rather than merely missing a feature.
Requesting `colorSpace: 'display-p3'` did not fix it: that widens the gamut without adding
bits, which is a different problem from the one HDR has.

Replaced with a plain `<img id="pic">` and `object-fit: contain`. The browser composites it,
so decode, colour management and HDR tone mapping all stay in the browser, where they handle
whatever the display can actually do. `object-fit: contain` is the identical contain fit, so
`contain()`, `measure()`, `draw()` and the whole rAF loop are gone, along with the dpr
bookkeeping.

WebGPU with a 16-bit float surface was the alternative and was not taken: it needs device
init, a render pipeline, texture upload and the tone mapping the browser was already doing,
to end up in the same place, for a large amount of code in a viewer whose point is to be
small. `<img>` is both the more correct pipeline and the smaller one.

## Open list and wheel

Added a toggle that opens a panel of the current set, with the current file marked and
scrolled into view, rows that jump on click, and a **Forget** button.

**Forget is a memory operation.** The object URL keeps the blob alive and every `File` in the
list keeps a handle to its bytes, so dropping a folder of large images leaves them resident
even though only the current one is decoded. `Viewer.destroy()` now routes through
`setImages([], 0)`, which revokes the URL, empties the list, detaches the `<img>` and fires
`onempty(false)`; `onempty` is the single place that reacts to the set becoming empty, so the
empty state, the toggle, the wheel accumulator and the list all clear from one signal.

**Wheel** maps to next/previous behind a threshold and a cooldown. A trackpad flick emits
dozens of small deltas; without a threshold one gesture pages through an entire folder. The
dominant axis wins so horizontal swipes work, `ctrl`+wheel is left alone so browser zoom
survives, and the wheel is not claimed over the list panel.

Two bugs found while building it, both caught by the harness:

- **Scrolling the list paged the image.** The handler is on `window`, so wheel events over
  the panel both scrolled the list and advanced the viewer. Guarded with `panel.contains`.
- **A half-accumulated flick survived into a new set.** Open a new folder mid-gesture and the
  carried-over delta fired a step immediately. The wheel state is now cleared in `onempty`.
  The test for it asserts that a sub-threshold delta stays sub-threshold, which is the only
  thing that distinguishes a cleared accumulator from a full one.

The list is built when the panel opens and when the set changes, never per keystroke;
navigation only moves a class and calls `scrollIntoView({ block: 'nearest' })`. One delegated
listener on the `<ol>`, so a 5000-row list costs no per-row closures.

Two harness fidelity gaps surfaced along the way and were fixed rather than worked around:
`addEventListener` handlers were called without a `this` binding, and elements created by
`createElement` were not linked into the markup hierarchy, so `contains` could not work.

## Judgment calls

- Hidden (dot) directories are skipped while walking. They hold no viewable content and
  walking `.git` on a large tree is pure cost.
- `webkitGetAsEntry` rather than `getAsFileSystemHandle`: one code path instead of two, and
  it is the more widely supported of the two.
- Failed decodes are reported, not skipped. Silently advancing would read as a viewer bug.
- The `<img>` carries `draggable="false"` and the stage `user-select: none`, so clicking
  through a folder neither starts an image drag nor flashes a text selection.
- The list panel overlays the image rather than shrinking it, so the fit stays a whole-page
  one. Paging is unaffected; the panel is translucent and the image remains visible behind it.
- The wheel threshold is 40 with a 120 ms cooldown, tuned for a mouse notch. A trackpad needs
  a longer flick for the same result, which is the intended behaviour, not an accident.

## Second round — info into the title, the list as a drawer

Four changes, all in the same direction: less on the picture, and the list reachable without
looking for a control.

**Info moved to the window title.** The overlay at the bottom of the stage carried the name,
the position and the pixel size. It duplicated what the title bar can already show, it sat on
top of the image, and it faded in and out for no reason. It is gone; `Viewer.onchange` writes
`name · 3/12 · 7680×4320` into `document.title` and the page itself has no chrome. The
decode failure stays on the stage, because that is the one thing the user has to act on and a
tab title is not where a report belongs.

**The list is a drawer with no handle.** The first attempt kept a **Files** button in the
corner and made the edge a second way in. That was the wrong shape: the page still carried two
controls, and the button sat inside the edge strip, so moving toward it opened the panel and
the click that followed closed it again.

The bar is gone. The pointer within 28 px of the left window edge pulls the list out, the
pointer moving past 320 px — the panel's right edge and a little — pushes it back, and one
`pointermove` handler runs both directions. A press held 450 ms toggles it, which is the same
gesture on a touch screen where no edge is ever hovered; it is cancelled by `pointerup`,
`pointercancel` and by more than 12 px of travel, so it cannot fire at the end of a drag.
`contextmenu` is swallowed on the stage, because the browser's own touch menu lands exactly
where the long press is. `F` and `Esc` drive the same pair from the keyboard.

The one-way guard the first attempt needed is gone with it: a drawer that closes when the
pointer leaves cannot be reopened by the pointer that closed it, because that pointer is the
one that left.

**A copy glyph at the end of every row**, so a path is copied from the row it belongs to
rather than from the file on screen. The glyph is one `<svg>` in a `<template>`, parsed once
and cloned per row — a 5000-row folder pays for one parse, not 5000. The click is delegated:
`closest('.cp')` tells copy from jump, and a copied row hands focus straight back, because a
focused button swallows the arrow keys that page the image. `C` still copies the file on
screen, which is the only copy there is while the drawer is shut.

The clipboard is reached through the async API only, reporting all three outcomes — copied,
refused, and no clipboard at all, which is what a page on plain `http://` gets. No
`execCommand` fallback: it is a dead path in every browser this runs in.

**Rows now split into folder and name.** A deep path was a single line of text with
`text-overflow: ellipsis`, which cut the end off — the file name, which is the only part the
row is for. The folder is now the flex item that shrinks and the name is `flex: none`, so the
name is always the readable end and the folder is what gives way.

### Bug the harness caught

`Viewer.item()` was documented as "no index means the current image" by its only caller, but
read as `list[i < 0 ? index : i]`, and `undefined < 0` is `false`. So the no-argument call
fell through to `list[undefined]` and returned `null` — the copy button silently did nothing,
and the only symptom was a toast that never appeared. Fixed in the viewer, where the rule
belongs, and pinned with a test for no argument, negative, in range and out of range.

### Judgment calls

- The edge is on the left only, which is the side the panel lives on. Both sides would open a
  panel anchored to the left.
- The long press toggles. Pressing again is the only way to close it by gesture, and a press
  that opens something the user cannot dismiss is a worse bug than a surprising double press.
- Copying a row does not also jump to it. The row click is the jump; the glyph is the copy,
  and a press that did both would move the image out from under the pointer.
- The title carries the size only once the browser has decoded it, so it reads
  `a.png · 1/3` for the frame or two before the dimensions land, rather than `0×0`.
- Rows are not virtualised. A 5000-image folder is 5000 rows built once, on open; the
  previous round's decision to build on demand rather than per keystroke is unchanged.

### Harness additions

- `textContent` on the stub now walks children on read, so a row built from spans still reads
  as one string and the existing path assertions keep working.
- `className` and `classList` are kept in step on the stub, and `matches` understands a class
  selector, because the row's copy button is found with `closest('.cp')`.
- `cloneNode` and `firstChild` on the stub, so the cloned glyph is a real separate node: a
  shared one would move every row's icon at once, and the test asserts two rows do not share.
- `withFakeClock` swaps `setTimeout`/`clearTimeout` for the duration of a test, so a held
  press is tested by firing the timers the app queued rather than by sleeping. The snapshot
  before firing keeps a handler that re-arms a timer from looping.
- `navigator` is a getter on `globalThis` in Node 22, so the clipboard stub is installed with
  `Object.defineProperty`, and the app reads `navigator.clipboard` at call time so the harness
  can swap between the working, refusing and absent cases.

## Third round — events are not queued

Every navigation event used to become a request immediately, and the only thing standing
between a held key and a backlog was the token that let a superseded load be dropped after
the fact. The work still happened: a key held down repeats at the OS rate, a wheel or
trackpad flick keeps emitting, and each event made a blob URL and started a decode that the
next event immediately invalidated. The user sees the last few images of the burst and a
decoder working through a folder nobody asked for.

The rule is now one load in flight. `show()` returns early while a frame is still decoding,
so a step that arrives too early is dropped — no URL, no decode, no index movement, nothing
to catch up on. A navigation lands per decoded frame, and holding a key pages one image at a
time at the speed the images actually decode. `busy` is cleared in `onload` and in `onerror`,
so a file the browser cannot decode does not wedge the viewer.

The guard has one door out, and getting it wrong is the trap: `setImages()` clears `busy`
before it shows anything, because a new set is a replacement, not a step. Without that line
the *first* image of a newly opened folder would be dropped by its own load, and the viewer
would show nothing at all until the next key.

The token is still there, but it now answers a narrower question. A step can no longer
supersede another, so what is left is a set that was replaced mid-load — `destroy()`, or a
second folder opened over the first — and that load must not paint or write the title.

**Drops got the same treatment from the other direction.** A folder walk is async and a big
tree is slow, so a second drop can land while the first is still walking. Both walks ran to
completion and each called `load()` on the way out, so the set on screen went back to the
one that arrived *first* whenever the older walk happened to finish later. A drop counter
now marks each walk, and a result whose mark is no longer current is dropped. Here the
newest wins rather than the first, because a drop the user just made cannot be ignored: the
whole point of dropping is replacing what is on screen.

Both were confirmed against the pre-fix code — the viewer harness fails on
`one request while loading` (4 requests where there should be 1) and the app harness on
`the newest drop wins` (`slow.png` where `quick.png` is correct). The drop test releases the
two deferred walks newest-first, because releasing them in arrival order would let the
stale one land last by accident and the test would pass either way.

### Judgment calls

- A step is dropped, not deferred and not coalesced. Coalescing — remember the last
  direction and apply it once the frame lands — is smoother to hold a key with, but it *is*
  the queue: it makes the viewer work through every image the burst asked for, which is the
  thing being removed. A viewer that shows one image per decoded frame is honest about how
  fast it is going.
- `preventDefault` is still claimed while a frame is decoding, so space and the arrows do
  not scroll the page under a held key. The key does nothing visible for those few
  milliseconds, which is less jarring than the page moving.
- The drop counter is not reused for the pickers. A picker hands over a file list
  synchronously, so there is nothing in the air to order.

## Fourth round — drop reported "no images found" again

The first round's fix was right about the mechanism and incomplete about the timing, and the
same message came back. Two more causes, both confirmed by reproducing the old behaviour in
a throwaway diagnostic driven against the harness stubs, then folded into `test-app.js` as
assertions and checked to fail against the pre-fix code. The diagnostic itself was deleted
once its cases were assertions — it was a hundred lines of duplicated stub for four cases
that now live where the rest of the drop tests are.

**The capture was taken once, at the first `dragenter`.** Chrome does not fill
`dataTransfer.items` on that event — the drag data has not been fetched yet — so the capture
frequently returns nothing at all. The code retried on a *later* `dragenter`, but
`dragenter` only fires when the pointer enters an element: hover over the picture and drop,
and there is no second one. The drag then falls through to a spent item list and an empty
`dataTransfer.files`, and reports nothing found. `dragover` fires continuously for as long as
the pointer moves, so the capture is now retried there. It is still only taken once per drag
— `grab` skips while a capture is already held — so the hot path costs one length check.

**An empty walk discarded files the drop event was still carrying.** The fallback to
`dataTransfer.files` ran only when there were *no entries*, not when the walk of those
entries produced *no images*. A root that reads as empty — an unreadable directory, a
permission refusal — therefore threw away files that were right there on the event. The
fallback now keys off the walk's result.

`captureEntries` also tested the capability on `items[0]` alone. A drag carrying a string
alongside its files has an item without `webkitGetAsEntry`, and that one item vetoed every
real file in the drag. The test is per item now.

### Two things I tried and backed out

- Guarding `dragleave` on the transfer's own types. `dragleave`'s transfer is not dependable,
  and the `dragenter` guard was not applied symmetrically to it, so the two stopped being a
  matched pair. Worse, the diagnostic that motivated it passed against the pre-fix code: the
  existing `<= 0` clamp already turned a negative depth back into zero, so the guard fixed
  nothing. Removed.
- Clearing the capture whenever a `dragenter` arrived at depth 0, on the theory that an
  unbalanced drag leaves a stale capture for the next drag. The diagnostic case for it failed
  *with* the fix in place — it walked the previous drag's tree either way — because the stale
  capture is only reachable through an unpaired leave, and unpaired leaves are a premise I
  could not test without a browser. Removed rather than shipped on an unverified assumption.

The comment left on the depth counter now says what the code actually does: the clamp is what
makes a mismatched leave harmless.

### Harness notes

- The new assertions empty the set first with `btnForget`. A drop that finds nothing keeps
  what was already loaded, so a count read against leftovers passes either way — the first
  version of the dragover test did exactly that and looked green against the broken code.
- `Viewer.item(0)` is read through a `|| {}` guard in the two new drop assertions. A set that
  never loaded has no item 0, and the unguarded read threw and took the rest of the run with
  it, hiding the other failures.
- `empty drop keeps list` now opens its own set. It was asserting against whatever the
  previous case happened to leave loaded, which my new cases changed.

## Fifth round — comparing `index.html` and `viewer-GLM.html`, fixing Chrome Windows `file://` drop, event queueing, and menu UX

Reviewed `TODO.txt` and compared `index.html` (`js/files.js`, `js/viewer.js`, `js/app.js`,
`css/app.css`) with `viewer-GLM.html`:

1. **Why drag & drop failed on Chrome Windows (`file://`) in both implementations while
   Firefox worked:**
   - The previous attempt in `index.html` called `webkitGetAsEntry()` during `dragenter` and
     `dragover` (`dropEntries` / `grab` / `captureEntries`). Per the HTML Drag and Drop spec,
     `DataTransfer` is in *protected mode* during `dragenter` and `dragover`; in Blink, calling
     `webkitGetAsEntry()` before `drop` creates an entry whose isolated filesystem is not yet
     registered, poisoning the drop when reused. Removed all `dragenter`/`dragover` entry
     capture leftovers.
   - On `file://` in Chrome, `webkitGetAsEntry()` constructs legacy `filesystem:file:///...`
     URLs that fail asynchronously with `EncodingError` inside `entry.file()` and
     `reader.readEntries()`. By the time that async callback failed, the synchronous `drop`
     event had already finished and the browser had cleared `dataTransfer.files`, so even the
     flat-file fallback saw 0 files.
   - Fixed in both `js/files.js` and `viewer-GLM.html` by synchronously capturing in `drop`:
     (a) `item.getAsFileSystemHandle()` promises (File System Access API, which uses native OS
     handles and works for both folders and files on `file://` in Chrome),
     (b) `item.webkitGetAsEntry()` entries (works in Firefox), and
     (c) a synchronous snapshot of `dataTransfer.files` / `item.getAsFile()` before any async
     continuation.

2. **Why `index.html` still queued/advanced on next/prev with large images:**
   - In Firefox, `img.onload` on a `blob:` URL fires as soon as the header is read (< 1 ms),
     before pixel decoding completes. `js/viewer.js` now awaits `img.decode()` inside `onload`
     when available so `busy` stays set until pixel decode is actually done.
   - In Chrome, decoding a large HDR image blocks the main thread until `onload`, so input
     events emitted during decode sit in the browser task queue and dispatch on the turn right
     after `onload`. A cooldown anchored at navigation *start* is already expired by the time a
     slow decode finishes. `js/app.js` now anchors the 100 ms debounce window (`navUntil`) at
     load/decode **completion** (`Viewer.onchange`), applies it to both keyboard and wheel
     navigation, and zeroes `wheelAcc` whenever `Viewer.busy()` is true or `now < navUntil`.

3. **Menu style, buttons, screen tint, and duplicate-file bug:**
   - Brought GLM's clean full-height dark drawer style and buttons into `index.html` and
     `css/app.css`: **Open Files**, **Open Folder**, **Forget**, and **X** (close) in the menu
     header, and **Path** (copy path) and **X** (forget individual file) buttons on each row.
   - Removed the screen-tinting `#overlay` in `viewer-GLM.html` and kept `index.html` tint-free.
   - Added deduplicated incremental file loading (`Viewer.addImages`) and single-file removal
     (`Viewer.remove`) in `js/viewer.js` (and `viewer-GLM.html`) so opening or dropping the
     same files again does not add duplicates.
   - Fixed the drawer open/close state (`inMenu`) so opening the menu with `F` or long press
     while the pointer is outside the panel does not close on the next pointer move before the
     pointer has entered the panel, and pressing outside closes the menu immediately.
